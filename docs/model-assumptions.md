# Model assumptions and controls

AeroSentinel is a deterministic environment for evaluating agents that inspect, repair and schedule operations. It is not validated satellite flight software. Its scientific claims are limited to the equations implemented below and their regression tests.

## State transition

An episode covers 5,700 simulated seconds. Sunlight ends at 3,600 seconds. Contact and observation windows come from the seeded, protected mission. Ordinary tool calls consume 30 simulated seconds. `step_orbit` advances 1-30 minutes. Integration splits exactly at window boundaries; elapsed time, energy and delivered work are not reconstructed from the final configuration.

| Quantity | Implemented model | Limitation |
|---|---|---|
| Solar generation | `calibration * 0.28 * 0.06 * 1361 * cos(pointing)` W in sunlight; zero in eclipse | Fixed orbit and array; no orbital propagator or degradation dynamics |
| Battery | Integrate generation minus load in Wh; clamp to 0-40 Wh | No cell electrochemistry, charger current regulator, efficiency or aging model |
| Bus voltage | `3.0 + 1.2 * SoC_fraction` V | Linear benchmark relation, not a measured discharge curve |
| Attitude | One scalar error, bias-driven drift or proportional damping toward deadband | No rigid-body dynamics or three-axis wheel simulation |
| Temperature | Integrate internal heat, sunlight heat and linear heat loss with a lumped heat capacity | No spatial thermal model or fourth-power radiation law |
| Radio margin | TX + antenna + ground gain - path loss - system loss - sensitivity - bandwidth penalty - pointing loss | Fixed mission propagation profile; simplified packet-loss threshold |
| Data | Baud/8, multiplied by 0.85 packet efficiency and contact duration | Half delivery at 0-3 dB; full at >=3 dB; no detailed coding/channel simulation |
| Observation | Duty cycle times seconds inside the observation window | Averaged instrument duty; exposure is a benchmark work metric |

Radio bandwidth penalty is `10*log10(baud/9600)` dB. The transmitter bus load is `8 + 2*10**(tx_dbm/10)/1000` W during contact. The observation payload draws 6 W times duty continuously, including outside its useful window.

`max_charge_rate_a`, `bus_voltage_nominal`, actuator torque/frequency and thermal polling fields are descriptive legacy fields. They do not affect state or score. The manual identifies them explicitly; presenters must not describe them as simulated mechanisms.

## Protected outcomes

The harness owns hardware facts, mission windows, energy allocations and success thresholds. The agent can read a copy in `docs/mission.json`, but editing that copy cannot redefine success. Physical telemetry is generated by the harness and is an observation, not a grading input. Unsafe hardware parameter changes and catastrophic events remain latched.

The four recovery components have weights 0.35 power, 0.25 temperature, 0.20 attitude and 0.20 communications. Observation missions multiply these by 0.8 and add a 0.20 exposure component. Progress is normalized against the initial no-op outcome. Every required check must pass independently, and a failed check prevents a success score even if the numeric raw score is high.

## Why scheduling is necessary

For a 600-second observation window, required useful exposure is 540 seconds. A constant duty must therefore be at least `540/600 = 0.90`. The mission's 1.2 Wh payload allocation over a 5,700-second episode permits constant duty at most `1.2/(6*5700/3600) = 0.1263`. These constraints cannot both hold. Enabling during the window and disabling afterward can satisfy them. Tests also accept another feasible schedule, so the verifier does not demand the reference sequence.

An early contact has a different constraint: after the window has passed, changing the final controller or radio configuration cannot create transmitted data in the past. The verifier integrates delivery through the actual history and checks the protected payload target.

## Scope of evidence

Reference runs prove selected generated instances are solvable through public tools. Scripted shortcuts test particular failure modes. Neither is evidence of model ability. Real model results are identified by deployment, seed and source fingerprint. No finite test set proves that every reward exploit, container escape or provider incompatibility has been eliminated.
